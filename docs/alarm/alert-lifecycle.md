# 告警生命周期设计

> **为什么需要这份文档**
>
> 现状：管理面能配策略，引擎能算出 `hit=true/false`，`alarm_history` 表有 29 列，
> `GET /api/alarm/histories` 能查。**中间那一段是空的** ——
> 没人定义「一次 `hit=true` 怎么变成一条告警记录」，也没定义它怎么恢复、
> 怎么重复通知、怎么处理。
>
> 缺这段的实际后果不是「少个功能」，而是**上线即数据污染**：
> 引擎按分钟评估，一个持续两小时的问题会产生 120 条重复告警，
> 而用户只想看到 1 条 + 若干次提醒。

---

## 1. 核心概念：活动告警

**一次 `hit=true` 不等于一条新告警。**

| 概念 | 含义 | 判据 |
| --- | --- | --- |
| **活动告警** | 已触发且**尚未恢复**的那一条 | `recovered_at IS NULL` |
| **已恢复告警** | 曾经触发、现已不命中 | `recovered_at IS NOT NULL` |

**同一条告警的身份** = `(policy_id, condition_id, object_id)`。

这三个字段合起来唯一确定「哪条策略的哪个条件在哪个对象上出的问题」：

```
策略 A 的 CPU>80 条件，在实例 12345 上反复命中 → 始终是**同一条告警**
策略 A 的 CPU>80 条件，在实例 12346 上反复命中 → **另一条**告警
策略 A 的内存>90 条件，在实例 12345 上反复命中 → **另一条**告警
```

> ⚠️ 为什么 `condition_id` 而不是 policy 级：
> 一条策略可能有 4 个条件同时命中。如果按 policy 级去重，
> 条件 2 恢复了、条件 1 还在命中时，用户看到的告警会**在条件之间来回跳**，
> 无法回答「到底是哪个条件出的问题」。
> 按 condition 级去重，每条问题独立成告警、独立恢复，才说得清。

## 2. 状态机

```
        引擎 hit=true                 引擎 hit=false
   （首次，无活动告警）              （有活动告警）
         │                              │
         ▼                              ▼
   ┌──────────┐   用户处理        ┌──────────┐
   │ 1 未处理  │ ────────────────▶ │ 2 已处理  │
   │          │                   │ 4 已恢复  │
   │ active   │                   └──────────┘
   │recov=NULL│                          │
   └────┬─────┘                          │
        │ 引擎 hit=false                 │
        ▼                                │
   ┌──────────┐                          │
   │ 4 已恢复  │ ◀────────────────────────┘
   │ recov=ts │
   └──────────┘
        │
        │ 用户也可以对未恢复的告警
        ▼
   ┌──────────┐
   │ 3 已忽略  │   忽略后**不再接收**引擎的状态更新
   └──────────┘   （但仍会被引擎恢复吗？见 §6）
```

### 2.1 各状态的精确语义

| status | 名称 | `recovered_at` | 含义 |
| --- | --- | --- | --- |
| `1` | 未处理 | `NULL` | 刚触发，用户还没看 |
| `2` | 已处理 | 可为 NULL | 用户处理过但**问题还在**（比如已扩容，指标还没降下来） |
| `3` | 已忽略 | 可为 NULL | 用户明确表示「这个不用管」 |
| `4` | 已恢复 | **NOT NULL** | 指标已回到正常 |

### 2.2 ⚠️ 「已处理」不等于「已恢复」

这是最容易搞混、也最影响用户信任的一点。

```
CPU 飙到 95% → 告警触发（status=1）
用户扩容了机器 → 点了「处理」（status=2）
   ↑ 此时 CPU 可能还有 89%，**问题没解决**，只是用户认领了
指标降到 60% → 引擎判定恢复（status=4，recovered_at=写入）
```

如果把「处理」当成「恢复」，会出现：
- 告警立刻消失，用户以为问题解决了，但过 5 分钟又冒出来
- 用户刚扩容完发现告警还在 → 认为系统有 bug

**所以「处理」只改 `handled_at`/`handle_action`/`handler_name`，不动 `recovered_at`。**
恢复只能由引擎写。

## 3. 状态转移表

| 当前 | 事件 | 新 status | 写入字段 |
| --- | --- | --- | --- |
| （无活动告警） | `hit=true` | `1` | `triggered_at`, 全部快照字段 |
| `1` | `hit=true` 再次 | `1`（不变） | `updated_at`；`notify_count` 按 §4 递增 |
| `1` | `hit=false` | `4` | `recovered_at`, `duration` |
| `1` | 用户处理 | `2` | `handled_at`, `handle_action='handle'`, `handler_name`, `handle_remark` |
| `1` | 用户忽略 | `3` | `handled_at`, `handle_action='ignore'`, `handler_name`, `handle_remark` |
| `2` | `hit=true` | `2`（不变） | `updated_at`；**不再通知**（见 §4.2） |
| `2` | `hit=false` | `4` | `recovered_at`, `duration` |
| `3` | `hit=false` | `4` | `recovered_at`, `duration`（见 §6 争议） |
| `4` | `hit=true` 再次 | `1`（**新行**） | 新告警，重新 `triggered_at` |

> ⚠️ 最后一行的语义：**恢复后再次触发 = 新告警，不是复活旧记录**。
> 否则 `triggered_at` 会停留在很久以前，用户按「最近告警」排序时找不到它，
> 而故障统计（本月发生几次）会全部算成 1 次。

## 4. 通知去重

契约 §1.6 已定义策略语义，本节定义**实现**：

> 告警产生后 24h 内按 `frequency` 重复；超过 24h 每天一次；`0` 表示生命周期内只通知一次。

### 4.1 通知决策

```
在 (now, last_notified_at) 上：
  frequency = 0   → 不再通知
  frequency = N   → now >= last_notified_at + N×60 秒 → 通知
```

### 4.2 已处理/已忽略后不再通知

| status | `frequency=0` | `frequency=N` |
| --- | --- | --- |
| `1` 未处理 | 首次通知 | 按 `N` 重复 |
| `2` 已处理 | 不通知 | **不通知** |
| `3` 已忽略 | 不通知 | **不通知** |
| `4` 已恢复 | 发一条**恢复通知** | 不再发 |

**理由**：用户点「处理」就是声明「我知道并在跟进了」。
继续每 5 分钟推一次，是在训练用户忽略告警 —— 告警一旦被无视就永久失去价值。

> ⚠️ 「恢复通知」是刻意保留的：用户需要闭环确认「问题真的好了」。
> 可以配 `notificationTemplate` 关闭它，但默认发。

### 4.3 `notify_count` 的含义

累计**成功发出**的通知次数，不是评估次数。它是「用户被骚扰了几次」的量化，
可用于后续优化阈值。

## 5. 并发正确性

多个采集/评估 worker 可能同时判定同一条告警「命中」。

### 5.1 只靠应用层不够

```php
// ❌ 先查后写：两个 worker 同时走到这里，都会认为「没有活动告警」
$active = AlarmHistory::where(...)->whereNull('recovered_at')->first();
if (!$active) { AlarmHistory::create([...]); }
```

`first()` 到 `create()` 之间有窗口。评估周期 1 分钟、并发 10 个 worker 时，
这个窗口足够产生重复行。

### 5.2 两道防线

**第一道 —— 数据库约束（最后防线）**

MySQL 不支持 `CREATE UNIQUE INDEX ... WHERE`，用**生成列**绕：

```sql
`active_key` VARCHAR(80) GENERATED ALWAYS AS (
  IF(`recovered_at` IS NULL,
     CONCAT(`policy_id`,':',`condition_id`,':',`object_id`),
     NULL)
) STORED,
UNIQUE KEY `uk_history_active` (`active_key`)
```

MySQL 的 UNIQUE 索引允许**多个 NULL 共存**，所以恢复后的行 `active_key=NULL`，
不参与唯一性检查；未恢复的行则受唯一约束保护。

**第二道 —— 应用层 `INSERT ... ON DUPLICATE KEY UPDATE`**

```php
Db::statement(
    'INSERT INTO alarm_history (...) VALUES (...) ON DUPLICATE KEY UPDATE
       `updated_at` = VALUES(`updated_at`), `notify_count` = `notify_count` + ?',
    [...]
);
```

⚠️ 这里必须**捕获重复键异常**（S-09：真实 `getCode()` 是 SQLSTATE `'23000'`，
errno 1062 在 `errorInfo[1]`），不能像早期版本那样降级成 422。

### 5.3 为什么两道都要

- 只有数据库约束 → 并发下应用层会收到异常，需要处理，否则评估任务失败
- 只有应用层 → 手工改库、数据修复脚本仍能写进重复行

## 6. 三个有争议的设计决策

### 6.1 「已忽略」的告警，恢复后要不要改状态？

**决策：改成 `4 已恢复`。**

忽略的是「这条告警」，不是「问题永远存在」。指标恢复正常了，
把告警标成「已忽略」会让人误以为它和「已恢复」有本质区别 ——
而两者唯一区别是「用户有没有表达过态度」。恢复是客观事实，应该如实记录。

### 6.2 `frequency=0` 的告警恢复时，还要不要通知？

**决策：要发一条恢复通知。**

`frequency=0` 的语义是「**重复**通知时不要发」，不是「完全不发」。
首次触发必发（否则用户永远不知道出事了），恢复也发（闭环）。
中间不重复。

### 6.3 `objectType=1`（全部对象）时 `object_id` 填什么？

**决策：填**具体的实例 id**，不填 0。**

表定义写的是「0 表示无具体实例」，但引擎是**按实例逐个评估**的
（心跳就是按 targetId 存的），所以一定有具体实例。

`object_id=0` 只在两种场景出现：
- 历史数据迁移遗留
- 未来的「全局级」告警（如「采集器全部挂了」，本项目暂无此语义）

⚠️ 这条要写进实现注释，否则有人看到 `0 表示无具体实例` 的注释
就会顺手填 0，导致所有实例的告警聚成一条。

## 7. 多对象展开

`objectType` 决定告警作用在哪些实例上：

| objectType | 展开方式 | 说明 |
| --- | --- | --- |
| `1` 全部对象 | 查询该 `policyType` 下当前账号有权限的**全部实例** | 无需用户逐个选，但引擎仍要逐实例评估 |
| `2` 指定实例 | `objectIds`（1-1000） | 直读 |
| `3` 实例分组 | `objectGroupIds` → 组内实例 | 需要分组服务的接口 |
| `4` 多维筛选 | `objectFilters` → 匹配实例 | 需要资源查询服务 |

### 7.1 ⚠️ 1000 个实例 × 4 个条件 = 4000 次求值

`objectType=2` 上限 1000 个实例，条件上限 4 条。
相对判据下每条条件还要读 N 个基线点。

**这是本设计里最大的性能悬崖，必须在设计阶段就面对**：

- 单实例单条件的求值应是 **O(1) 次采样读取**（当前窗口 + 基线窗口各 1 次）
- 4000 次求值 = 8000 次读取，若每次一次查询就是 8000 次 IO

**缓解方向**（按优先级）：
1. **批量取样**：一次取整个时间窗的所有采样，内存里算，而不是按点查
2. **按 metric 分组**：同一策略的 4 个条件若用同一指标，只取一次数
3. **并发求值**：按实例分片

本项目只做前两项的**接口预留**（`SampleRepository::fetch` 已支持时间范围查询，
天然适合批量取），具体调度策略属部署侧决策。

### 7.2 展开失败的处理

「全部对象」查询可能因为权限变更、实例已销毁而少拿到几个实例。
**已存在的实例不受影响**，只是少评估了。**不能**因为展开失败就跳过整条策略 ——
那会让一个非关键故障导致所有告警停摆。

## 8. 告警风暴

`frequency` 是**每条告警独立**的去重，不是全局限流。

极端场景：1000 个实例同时触发 → 1000 条告警 × 首次通知 = 1000 条推送。

**本设计的明确边界：不解决风暴抑制。**

风暴抑制（分组、聚合、依赖抑制、值班轮转）是独立议题，需要产品决策：
- 什么算「同一个问题」？同实例多条件？同服务多实例？
- 抑制窗口多长？
- 抑制后怎么在 UI 里表达「已抑制」？

**但本设计必须为它留出接口**：告警身份三元组 `(policy_id, condition_id, object_id)`
和「通知时机」分离 —— 未来加抑制层时，只需在**通知决策**前面插一道，
不用改告警的生成与恢复逻辑。

## 9. 与现有部分的接口

```
┌──────────────┐
│ PolicyEvaluator │ → Verdict(hit, reason, value, baseline, deviation)
└──────────────┘
        │
        ▼
┌──────────────────────┐
│ 告警状态机（本设计）   │ → 决定：新建 / 更新 / 恢复
└──────────────────────┘
        │
        ├──▶ alarm_history（落库）
        │
        └──▶ 通知决策（frequency + status）→ 通知服务（不在本项目）
```

**职责边界**：
- 引擎（`App\Engine`）只负责**求值**，不碰 `alarm_history`
- 状态机负责**状态转移 + 落库 + 通知决策**
- 通知投递（渠道对接、重试、降级）不在本项目

### 9.1 未实现清单

| 项 | 状态 | 理由 |
| --- | --- | --- |
| 状态机代码 | ❌ 未实现 | 本次只出设计；实现需先定「恢复的判定宽限期」 |
| `active_key` 生成列 + 唯一索引 | ❌ 未实现 | 需要迁移；见 §5.2 的完整 DDL |
| 通知投递 | ❌ 不做 | 通知服务的职责 |
| 风暴抑制 | ❌ 不做 | 需产品决策，见 §8 |
| 多对象批量求值 | ❌ 未实现 | 需先定采样批量接口的性能目标 |

> ⚠️ 状态机代码**故意没写**：还有一个设计问题没解决 ——
> **恢复的宽限期**。指标在阈值附近抖动时，会出现
> 「命中 → 不命中 → 命中 → 不命中」，每 1 分钟评估一次的话
> 会产生大量「已恢复」记录又立刻新开一条。
> 标准做法是恢复后观察 N 个周期再确认，但 N 取多少、
> 与 `continuity` 什么关系，是产品决策。
> 在这个问题定下来之前写状态机，等于把一个必然会改的设计固化进代码。

## 10. 已落地的部分（v1.3.1）

### 10.1 `active_key` 生成列 + 唯一索引（已落地并真跑验证）

迁移 `2026_10_12_001000_add_alarm_history_active_key.php`，
`schema.sql` 已同步。真实 MySQL 8.0.46 上验证的行为：

| 场景 | 期望 | 实测 |
| --- | --- | --- |
| 同键首次插入 | 成功 | ✓ |
| 同键再次插入（均未恢复） | **1062 拒绝** | ✓ `Duplicate entry '9001:1:555'` |
| 不同 `object_id` | 成功 | ✓ |
| 恢复后同键再插入 | 成功（新建一条） | ✓ |
| `up()` 重跑 | 无异常 | ✓ |
| `down()` 回滚 | 列与索引都移除 | ✓ |

**脏数据清理**也真跑过：造 9 行重复活跃 → 迁移后保留最早 1 行、
其余 8 行标记为已恢复 → 加唯一索引成功。

⚠️ 清理必须在 `ADD UNIQUE KEY` **之前**。顺序反了的话，
有脏数据的库上 ALTER 会直接失败，而生成列已加上、
唯一索引没加上 —— 留下一个「有列无约束」的半完成状态，
之后的重跑会一直撞同一个错。

### 10.2 守卫

`verify-schema-consistency.mjs` 新增 6 条断言，覆盖：
生成列类型、列序（必须晚于 `recovered_at`）、唯一索引存在性、
迁移里有对应 DDL、清理逻辑存在、**清理在加索引之前**。

其中「顺序」这条是补牙补出来的：守卫第一次跑就报出我的迁移顺序反了。

### 10.3 迁移幂等守卫也修了一版

`verify-migration-idempotent.mjs` 的「是否被存在性探测保护」判定重写：
从「认固定函数名」改成「往上找最近的 `if (...)`，看条件里有没有探测」。

原写法有两个方向的错：
- 只认 `columnExists` / `addColumnIfMissing` → 误报 `indexExists` 保护的 DDL
- 「文件里出现过探测函数就整份放行」→ 放过真正的裸 DDL（更早的 bug）

现在带**自检**：用 4 个内存里的反例验证规则本身有效
（能抓裸 DDL、也能放行被 if 保护的 DDL）。
守卫脚本自己失效却输出 ✓ 是这类工具最常见的失效方式。

## 11. 仍然缺什么

| 项 | 为什么没做 |
| --- | --- |
| **状态机代码** | 恢复宽限期没定。指标在阈值附近抖动时，「命中→不命中→命中」会产生大量「已恢复」记录又立刻新开一条。标准做法是恢复后观察 N 个周期再确认，但 N 与 `continuity` 的关系是产品决策 |
| 告警事件的生成侧代码 | 依赖状态机 |
| 通知投递 | 通知服务的职责（渠道对接、重试、降级） |
| 多对象批量求值 | 需要先定采样批量接口的性能目标（§7.1 的 4000 次求值悬崖） |
| 风暴抑制 | 需要产品定义「什么算同一个问题」（§8） |

⚠️ 这份文档最要紧的一句话：**唯一性约束落地了，但「什么时候算恢复」还没定。**
在那之前不写状态机，是刻意的 —— 把一个必然会改的设计固化进代码，
比慢三天更贵。
