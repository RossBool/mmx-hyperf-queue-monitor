# 阈值校准方法论

> 本文回答一个问题：`metrics.md` 里的 `defaultThreshold` **凭什么是这个数**。
>
> **先说清楚本文做不到什么**：我手上没有你的真实监控时序数据，
> 所以本文**不会**给出「经过真实数据校准的阈值」。
> 能做的是把每个默认值的**推导依据**写清楚、标出哪些默认值在
> 结构上就站不住，并给出拿到真实数据后该怎么算的**可执行流程**。
> 把没有依据的数字包装成「已校准」，比不校准更糟。

---

## 1. 结论先行

38 个指标里，`defaultThreshold` 分三类：

| 类型 | 数量 | 依据 | 能不能脱离真实数据校准 |
| --- | --- | --- | --- |
| **A 类 · 有硬上限** | 8 | 协议/内核/硬件的物理上限 | **能**，推导即校准 |
| **B 类 · 有行业惯例** | 26 | 运维经验值，同行普遍这么设 | **部分**，能定初值，但必须按自己的历史分位复核 |
| **C 类 · 容量相关** | 4 | ⚠️ **没有固定阈值可用** | **不能**，见 §4 |

**C 类的 4 个指标（`DiskReadIops` / `DiskWriteIops` / `DiskReadTraffic` / `DiskWriteTraffic`）
当前的默认值是错的**，不是「没校准」，是「结构上不可能对」。详见 §4。

---

## 2. A 类：有硬上限，阈值就是上限

这类指标的阈值不是经验值，是**物理边界**。越过即故障，没得商量。

| 指标 | 默认值 | 硬上限来源 |
| --- | --- | --- |
| `FileDescriptorUsageRate` | `> 80`% | FD 硬上限 = `ulimit -n` / `LimitNOFILE`。超过即 `EMFILE`（「Too many open files」是 Linux Top 5 故障） |
| `InodeUsageRate` | `> 85`% | 文件系统 inode 总数。用完即 `ENOSPC`，**且与磁盘空间正交**——盘还空着但 inode 用完时，任何文件创建全挂 |
| `HttpSuccessRate` | `< 99`% | 无硬上限，但 99% 是 SLO 通行的下界（对应 3 个 9） |
| `MysqlConnectionRejectCount` | `> 0` 次 | **零容忍**。连接被拒 = 连接池耗尽，不会是正常波动 |
| `MysqlDeadlockCount` | `> 0` 次 | **零容忍**。死锁是应用层缺陷，1 分钟窗口内出现即需排查 |
| `MysqlLockWaitTime` | `> 1000` ms | 超过 1 秒的锁等待已足以让事务超时；InnoDB 默认 `innodb_lock_wait_timeout=50s`，等到 50 秒时业务早该挂了 |
| `DiskDaysToFull` | `< 7` 天 | 取 7 天是因为「一个常规发版/清理周期」。这是**约定**不是硬上限，归 B 类更准，但先列在这里方便对照 |

> `> 0` 的两个指标（死锁 / 连接被拒）容易被当成「太敏感会误报」。
> 实际不会：这两类事件在健康系统里出现频率极低，
> 而漏报的代价（连接池耗尽 → 全站 5xx）远高于误报。
> 如果嫌吵，正确做法是调 `continuity` 或 `frequency` 聚合窗口，**不是**把阈值调大。

---

## 3. B 类：行业惯例，必须用自己的历史分位复核

这 26 个指标的默认值是运维经验值。它们是**合理的起点**，
但经验值隐含了一个前提：**你的业务和别人的业务差不多**。

这个前提经常不成立。一个每天 200 万 PV 的站和一个每天 2000 PV 的站，
「CPU 80%」对两者的含义完全不同。

**复核方法**（拿到数据后必做）：

```
阈值 = P99(历史健康期该指标)  上浮 20%
```

例：某站 `HttpAvgDuration` 历史 P99 = 320ms，
则初值 = 320 × 1.2 ≈ 384ms，而不是当前的 500ms。

用 P99 而不是 max：max 会被单次网络抖动/GC 停顿拉飞，
按 max 设阈值必然误报到没人看告警。

**为什么不直接用 P99×1.2 替换默认值**：因为那需要真实数据，
而字典是**通用**的，不该被某一个站点的数据绑死。
默认值给的是「不知道你的数据时从哪开始」。

## 4. C 类：容量相关指标——**当前的默认值是错的**

这是本文最重要的发现。

### 4.1 问题

腾讯云官方云盘性能公式（来源见 §6）：

| 云盘类型 | 随机 IOPS | 最大吞吐 |
| --- | --- | --- |
| 高性能云硬盘 | `min{1800 + 容量(GiB) × 8, 6000}` | `min{100 + 容量 × 0.15, 150}` MB/s |
| 通用型 SSD | `min{1800 + 容量 × 15, 10000}` | `min{100 + 容量 × 0.2, 190}` MB/s |
| SSD 云硬盘 | `min{1800 + 容量 × 30, 26000}` | `min{120 + 容量 × 0.2, 260}` MB/s |
| 增强型 SSD | `min{1800 + 容量 × 50, 50000}` | `min{120 + 容量 × 0.5, 350}` MB/s |
| 极速型 SSD | `min{4000 + 容量 × 100, 50000}` | `min{120 + 容量 × 0.5, 350}` MB/s |
| ↳ 额外性能 | 可加至 **100 万 IOPS** | 可加至 **4000 MB/s** |

注意 IOPS 上限的跨度：**100GB 高性能盘 2600 → 极速型+额外性能 1,000,000**，
差 385 倍。

### 4.2 当前默认值两头都不对

| 指标 | 当前默认 | 在低端盘（100GB 高性能，2600 IOPS） | 在高端盘（极速型+额外性能，100 万 IOPS） |
| --- | --- | --- | --- |
| `DiskReadIops` | `> 5000` | **永远不触发** —— 盘根本到不了 5000 | **永远触发** —— 告警风暴 |
| `DiskWriteIops` | `> 5000` | 同上 | 同上 |
| `DiskReadTraffic` | `> 100` MB/s | 100GB 高性能上限 115 MB/s，勉强能响 | 上限 4000 MB/s，**永远不触发** |
| `DiskWriteTraffic` | `> 100` MB/s | 同上 | 同上 |

「永远不触发」比「误报」更危险：**它制造了一种虚假的安全感**——
用户看到这条策略是「开着的」，以为 IO 打满有人管，实际它一次都不会响。
而 `DiskUsageRate` 之类指标全绿时，用户没有任何线索知道 IO 早满了。

> 注：`DiskReadTraffic` / `DiskWriteTraffic` 是 v1.0 就有的指标，
> `DiskReadIops` / `DiskWriteIops` 是 v1.1 新增的。
> **同一个缺陷跨越了两个版本**，说明它不是「新增指标没想清楚」，
> 而是整个字典的设计假设没被检验过。

### 4.3 为什么不能「取个中间值」

中间值（比如 IOPS 阈值设 2000）在**两个方向上同时失效**：
- 高性能盘上仍然几乎不响（用户以为有兜底，实际没有）
- 极速型盘上变成常态告警（用户很快就把告警静音了）

**一个全局常量无法覆盖 385 倍的动态范围。这不是调参问题。**

### 4.4 正确解法：v1.1 的相对判据

这正是 v1.1 引入 `compareMode: relative` 要解决的场景：

```
DiskReadIops:  compareMode = relative
               baselineType = day        （与昨日同期比）
               operator     = >
               threshold    = 200        （相对基线涨超 200% 才告警）
```

语义变成「**比我自己昨天忙的时候还忙 2 倍**」，
自动适配任意云盘类型、容量和性能配置。

**这就是为什么 v1.1 的相对判据不是「锦上添花」**——
在容量相关指标上，它是唯一能工作的表达方式。

### 4.5 保留绝对阈值，但改语义

绝对阈值仍有用，用途变成**「硬件红线」**而不是「业务异常」：

| 指标 | 建议的绝对阈值 | 语义 |
| --- | --- | --- |
| `DiskReadIops` | `> 60000` | 已远超绝大多数云盘基线，大概率是异常而非业务高峰 |
| `DiskWriteIops` | `> 60000` | 同上 |
| `DiskReadTraffic` | `> 800` MB/s | 只有极速型 + 额外性能才可能到，视为红线 |
| `DiskWriteTraffic` | `> 800` MB/s | 同上 |

设这么高会有意「牺牲灵敏度」：它抓不到「慢速但持续打满」的情况。
**这正是它该交给相对判据的原因**——两个判据分工：
- 相对判据抓「相对异常」（灵敏，会误报）
- 绝对红线抓「绝对灾难」（迟钝，不误报）

⚠️ **本次未改动这 4 个默认值。** 理由：改字典要同步 contract / metrics.md /
前端类型 / 一致性守卫四处，而「60000 / 800」这个数同样是我拍的——
拍完再拍一次只是换个人来猜。正确顺序是：
**先用相对判据在真实环境验证，拿到数据后再回来定红线。**

## 5. 可执行校准流程

有了真实数据后，按这个流程跑，不要手算。

### 5.1 数据准备

需要每个指标至少 **14 天**的时序数据，且这段时间业务无已知故障。
14 天的理由：要覆盖 2 个完整周周期（消除工作日/周末差异），
并且 `baselineType: week` 的同比需要至少 1 个完整周基线。

数据格式：CSV，两列。

```csv
timestamp,value
2026-09-01T00:00:00Z,312.5
2026-09-01T00:01:00Z,298.1
```

### 5.2 跑校准脚本

```bash
node scripts/calibrate-thresholds.mjs \
  --input data/CpuUtilizationRate.csv \
  --metric CVM.CpuUtilizationRate \
  --out data/CpuUtilizationRate.calibrated.json
```

脚本会输出：P50 / P95 / P99 / P99.9、最大值、
MAD（中位数绝对偏差，用于识别离群点）、异常点占比，
以及**推荐阈值**和**推荐连续周期数**。

### 5.3 人工复核清单

脚本给的是**候选值**，下面每一条都要人过一遍：

- [ ] 推荐阈值下，异常点占比在 **0.1% - 1%** 之间？
      低于 0.1% → 太灵敏，会被淹没；高于 1% → 太钝，抓不到真问题
- [ ] 按推荐阈值回放历史故障，那次故障**触发了吗**？
      （这是唯一能证明阈值有效的检验）
- [ ] 按推荐阈值回放正常期，**误报了几次**？能不能接受？
- [ ] 指标的**量纲**对吗？把 IOPS 的历史数据和带宽指标混在一起算过没有？
- [ ] 这个指标是**容量相关**的吗？如果是，§4 的结论适用，
      绝对阈值只作红线，业务异常交给相对判据

## 8. 补充：为什么「相对判据」是这 4 个指标的唯一解

§4.4 只说了结论，这里补上完整推导。

绝对阈值成立的前提是**「故障有绝对边界」**。
对 CPU、内存、FD 使用率成立——100% 就是满，跟机器多大无关。

对 IOPS / 吞吐不成立，因为云盘性能是**按规格售卖的**：
100GB 高性能盘 2600 IOPS，32TB 极速型盘 5 万 IOPS，
再叠加额外性能可以到 100 万。**故障边界跟着规格跑。**

于是任何全局常量都落在两难里：

```
阈值太低（如 1000）→ 极速型盘常态告警 → 用户静音 → 等于没有
阈值太高（如 50000）→ 小盘永远不响 → 制造虚假安全感 → 更糟
```

「虚假安全感」比误报危险得多：用户看到策略是开着的，
以为 IO 打满有人管，实际一次都不会响。而此时磁盘使用率、内存、
网络全绿，没有任何线索指向 IO 已经饱和。

**所以容量相关指标的正确表达是相对判据**：

| 配置 | 值 | 语义 |
| --- | --- | --- |
| `compareMode` | `relative` | 相对基线，不是绝对值 |
| `baselineType` | `day` | 与昨日同期比（消除工作日/周末差异） |
| `operator` | `>` | 上涨才算异常 |
| `threshold` | `200` | 相对基线涨超 200% 才告警 |

这套配置在 2600 IOPS 的小盘和 100 万 IOPS 的大盘上**语义一致**：
「比我自己昨天忙的时候还忙得多」。

这也是本项目坚持「相对判据用正交字段而不是新符号算子」的实际回报：
`compareMode` 与 `operator` 解耦之后，同一个 `>` 算子既能表达
「大于某个绝对值」也能表达「大于基线的 N 倍」，
而 `operator` 的枚举从头到尾没变过——**不需要迁移历史数据**。
