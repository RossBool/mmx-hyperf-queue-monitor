# 告警指标覆盖度 — 第一性原理分析

> 日期：2026-10-04
> 对象：`docs/alarm/metrics.md`（现有 28 个指标）对照契约 `contract.md` §1.1 / §1.2
> 方法：不从「腾讯云有什么指标」出发，而是从**监控系统为什么存在**推导它必须能发现什么。

---

## 0. 先回到第一性原理

监控系统存在的唯一理由是：**在用户发现之前，发现「用户在意的东西坏了」。**

把这个目标展开成一个可判定的命题，对每个候选指标只问三个问题：

| 判据 | 问题 |
| --- | --- |
| **R1 故障可达性** | 它对应的那类故障，用户**真的会遇到**吗？还是理论上存在但实际罕见？ |
| **R2 状态不可见性** | 这类故障发生时，它**不告警**，用户**多久**才会发现？ |
| **R3 现有覆盖** | 现有 28 个指标里，**有没有别的指标能间接发现**它？ |

R3 是关键：没有它，分析会退化成"指标越多越好"的堆砌。**能靠别的指标发现的就不是缺口。**

由此推导出**六类必须覆盖的故障语义**（下文称之为 A–F 类），
再逐类核对现有覆盖。

---

## 1. 六类必须覆盖的故障语义

### A 类 · 不可用 —— 「服务根本服务不了」

用户视角：点不开 / 全报错。**R2 = 用户立刻发现，我们等于没做。**

现有覆盖：`Http5xxCount` / `HttpSuccessRate` / `HttpTimeoutCount` / `ClbBackendUnhealthyCount`。

**🔴 缺口 A-1：流量断流完全不告警。**

`WEB.HttpRequestCount`（QPS）的 `defaultOperator` 是 `>`，阈值 `10000`。
它能发现「QPS 冲到一万」，**但发现不了「QPS 归零」**。

而「QPS 归零」恰恰是最严重的故障形态之一：服务进程还在、健康检查可能还过、
但一个请求都处理不了。此时所有现有指标的表现是：

| 指标 | 值 | 会告警吗 |
| --- | --- | --- |
| `HttpRequestCount` | 0 | ❌ `0 > 10000` 为假 |
| `Http5xxRatio` | 0 | ❌ `0 > 5` 为假 |
| `HttpSuccessRate` | 0 | ✅ **只有它会**（`0 < 99` 为真） |
| `HttpAvgDuration` / `P99` | 0 / 无数据 | ❌ |

**但 `HttpSuccessRate` 的兜底是有代价的**：QPS=0 时成功率分母也是 0，
不同监控系统对该情形的取值约定不同（部分实现返回 100%）。
**依赖一个语义未定义的指标去兜底最严重的故障，是不可接受的。**

> 结论：A-1 是**方法论级缺口**，不是「少一个指标」。

---

### B 类 · 变慢 —— 「还能用，但快崩了」

用户视角：能点，但转圈。**R2 = 用户先发现，体验已损坏。**

现有覆盖：`HttpAvgDuration` / `HttpP99Duration` / `MysqlSlowQueryCount`。

P99 已覆盖长尾，这是对的。但仍有两处：

* **B-1 `WEB.HttpMaxDuration`**：单次最坏耗时。P99 之后仍有 1% 的请求更慢，
  而在**低 QPS 服务**上这 1% 可能就是全部用户。
* **B-2 `CLB.ClbBackendResponseTime`**：CLB 侧观测到的后端耗时。
  与 `WEB.HttpP99Duration` 交叉可定位「慢在 LB 还是后端」——
  这是 `ClbHttp5xxRatio` 已经采用的定位思路（文档 §1.3 明确写了「可交叉定位」），
  响应时间却没跟上。**同一设计原则只落实了一半。**

---

### C 类 · 错误 —— 「返回了错的东西」

用户视角：报错 / 数据不对。

现有覆盖：`Http4xxCount` / `Http5xxCount` / `Http5xxRatio` / `MysqlSlowQueryCount`。

* **C-1 `MYSQL.MysqlDeadlockCount`（死锁数）** 与 **`MysqlLockWaitTime`（锁等待时长）**：
  死锁是 MySQL 最常见的"隐性故障"，表现为间歇性请求超时，
  而现有的慢查询指标查的是**单条 SQL 慢**，不是**互相等锁**。
  R3 复核：`MysqlSlowQueryCount` 发现不了死锁——死锁的两条 SQL 各自都不慢。
* **C-2 `MYSQL.MysqlConnectionRejectCount`（连接被拒数）**：
  触及 `max_connections` 时 MySQL 直接拒绝新连接。
  R3 复核：`MysqlConnectionRatio` 只在**连接数逼近上限**时告警；
  而瞬时打满再回落时，采样点上 ratio 可能根本没超阈值，但**用户已经被拒了**。

---

### D 类 · 将耗尽 —— 「还能跑，但快没了」

用户视角：事后才发现（已经挂了才知道）。**R2 = 天级。**

现有覆盖：CPU / 内存 / 磁盘 / IO / 连接数。

* **D-1 `CVM.FileDescriptorUsageRate`（FD 使用率）**：
  R1 极高——Linux 上"Too many open files"是 Top 5 故障，
  且**通常先于内存耗尽出现**。R3 复核：内存/连接数**都发现不了它**
  （一个进程可以只打开文件、不占多少内存、连接数也正常）。
* **D-2 `CVM.InodeUsageRate`（inode 使用率）**：
  磁盘有空间但 inode 用完 → 任何文件创建失败（写日志、落临时文件全挂）。
  R3 复核：`DiskUsageRate` 看的是**块**，inode 是**另一个维度**，完全正交。
  这是最典型的「指标看着全、实际有洞」——D 线覆盖了磁盘**容量**却漏了磁盘**可用性**。
* **D-3 `CVM.DiskDaysToFull`（预计写满天数）**：
  现有 `DiskUsageRate` 阈值 85%。对一块 50G、每天涨 2G 的盘，
  85% 时还剩 3 天；对一块 1T、每天涨 2G 的盘，85% 时还剩 75 天。
  **同一个绝对阈值对增速差异巨大的磁盘含义完全不同。**
* **D-4 `CVM.DiskReadIops` / `DiskWriteIops`**：
  现有只有吞吐（`MB/s`）。随机小 IO 场景（大量小文件、日志、缓存）吞吐很低但 IOPS 打满。
  MB/s 与 IOPS 是两个正交维度，**缺一不可**。

---

### E 类 · 异常 —— 「值不极端，但不正常」

用户视角：说不清哪里怪，但业务不对。

**🔴 缺口 E-1（最大的一条）：现有 28 个指标全部是静态绝对阈值，没有任何一个能发现"相对于自身基线的异常"。**

这不是缺一个指标，是**缺一整类判据**。它导致下面这些故障全部逃逸：

| 故障 | 绝对阈值视角 | 为什么逃逸 |
| --- | --- | --- |
| QPS 从 100 跌到 10 | 阈值 10000 | 10 远低于阈值，健康 |
| 错误率从 0.1% 涨到 8% | `Http5xxRatio` 阈值 5 | 会触发 ✅（这个是侥幸） |
| 延迟从 20ms 涨到 300ms | `HttpP99Duration` 阈值 1000 | 没触发 |
| 夜间流量归零 | 阈值 10000 | 不触发 |
| 某接口 100% 失败但量小 | `Http5xxCount` 阈值 10 | 3 次 < 10，不触发 |

**注意第 1 行和第 5 行**：都是"看起来一切正常，实际服务已经不可用或严重降级"。

契约 §1.5 的 `operator` 只有 `> >= < <= == !=` 六个**比较**算子，
**没有同比/环比/突变判据**。这意味着 E 类整类无法表达。

> 这是**契约级扩展**，不是加指标能解决的。详见 §3 的 D 方案。

---

### F 类 · 无数据 —— 「监控系统自己瞎了」

用户视角：一切正常（因为什么都没发生）。

**🔴 缺口 F-1：完全没有。**

指标上报中断 / 采集 agent 挂了 / 写库失败 —— 此时所有现有指标的读数是
"0" 或"上次值"或"空"，三者都可能被解释成"业务正常"。

**这是最危险的缺口，因为它静默。** 前面 A–E 类的缺口至少会导致"某个故障不被发现"，
F 类的缺口是"**所有故障都不被发现，且系统看起来一切正常**"。

> F 类同样不是普通指标 —— 它需要**数据新鲜度 / 心跳**机制。
> 契约 §2 的 `alarm_history` 是"故障发生后"的记录，没有"应该发生却没发生"的表达。

---

## 2. 结构性缺口：契约声明的 5 种监控类型，字典只覆盖了 2 种

这是分析过程中发现的、比任何单个指标都严重的问题。

契约 §1.1 声明 `monitorType` 有 5 个合法值，但联动表同时写明：

> `3` / `4` / `5` → v1.0 暂无策略类型，**不可选**（选了返回 422）

而 `metrics.md` §0.2 的 namespace 映射表只有 4 个 namespace，覆盖 monitorType 1 和 2。
**monitorType 3/4/5 没有任何指标。**

### 2.1 前端现状：这是一个用户走不出去的死胡同

`policy-form.vue` 的监控类型下拉遍历 `alarmMonitorTypeOptions`（**全部 5 项**），
没有按联动表过滤。选中 3/4/5 后：

```
监控类型：前端性能监控
策略类型：（下拉被禁用，因为 policyTypeOptions 为空）
        该监控类型在 v1.0 暂无可用策略类型
```

**用户无法完成向导，也无法取消这个选择**——只能退回去重选。

R2 评估：不是"体验不好"，是**功能不可用**。审查报告 S-14 记录过
"`monitorType ↔ policyType` 联动零约束"，但只谈到了数据库 CHECK 缺约束，
**没有发现 UI 层把不可选的值提供给了用户**。

### 2.2 两条修法

| | 方案 | 影响面 |
| --- | --- | --- |
| **F-a** | **UI 不提供不可选项**（推荐） | 只改前端联动表 + 下拉过滤，零契约变更 |
| **F-b** | **补齐 RUM / PING_SITE 的 policyType 与指标** | 契约 §1.2、CHECK 约束、前端联动表、后端校验、指标字典全动 |

**F-b 是产品决策**，不该由一次技术分析单方面推动。§3 列为待拍板项。

## 3. 汇总：按「是否需要动契约」分流

### 3.1 无争议的补齐（不动契约，动手即做）

| 编号 | 指标 | namespace | 缺口来源 | R1 | R2 |
| --- | --- | --- | --- | --- | --- |
| A-1 | `HttpRequestCount` 增加**反向**配置用法 | WEB | 见 §1 A 类 | 高 | 秒级 |
| B-1 | `HttpMaxDuration` 最大响应延迟 | WEB | B 类 | 中 | 分钟级 |
| B-2 | `ClbBackendResponseTime` 后端响应时间 | CLB | B 类 | 中 | 分钟级 |
| C-1 | `MysqlDeadlockCount` 死锁数 | MYSQL | C 类 | 中 | 分钟级 |
| C-2 | `MysqlLockWaitTime` 锁等待平均时长 | MYSQL | C 类 | 中 | 分钟级 |
| C-3 | `MysqlConnectionRejectCount` 连接被拒数 | MYSQL | C 类 | 中 | 秒级 |
| D-1 | `FileDescriptorUsageRate` FD 使用率 | CVM | D 类 | **高** | 分钟级 |
| D-2 | `InodeUsageRate` inode 使用率 | CVM | D 类 | 高 | 分钟级 |
| D-3 | `DiskDaysToFull` 预计写满天数 | CVM | D 类 | 高 | **天级** |
| D-4 | `DiskReadIops` / `DiskWriteIops` | CVM | D 类 | 中 | 分钟级 |
| F-a | UI 过滤不可选的 monitorType | — | §2.1 | — | **功能不可用** |

**共 11 个新指标 + 1 个 UI 修复。**

### 3.2 需要产品拍板（**不应由技术分析单方面决定**）

| 方案 | 内容 | 为什么必须拍板 |
| --- | --- | --- |
| **C-1** | 补 `RUM` / `PING_SITE` 两个 policyType + 对应指标 | 契约 §1.2 枚举要扩、CHECK 约束要改、影响 P3 联动校验。**这是产品范围决策**（v1.0 是否做前端监控/拨测） |
| **D-1** | 增加同比/环比/突变算子（如 `> 基线均值 * 1.5`） | 现有 6 个算子都是单值比较。引入基线概念需要：基线窗口定义、最少样本量、冷启动行为。**契约 §1.5 的核心变更** |
| **E-1** | 无数据 / 心跳检测机制 | 需要新的数据模型（心跳表或 freshness 字段）+ 新的调度语义。**不是加指标能解决的** |
| **F-2** | 逐接口 / 逐实例粒度的指标 | 现在 `objectType` 支持"多维筛选"但指标都是聚合值。细粒度告警需要指标支持 tag 维度 |

**我的建议排序**：先做 §3.1（纯增益、无争议），
再评估 **C-1**（拨测是告警平台的基础能力，缺失影响最大），
**D-1 / E-1** 留到 v1.1 并单独立项。

## 4. 一条方法论结论

写这份分析时最反直觉的一点：

> **D 类（将耗尽）看起来覆盖得最全——CPU、内存、磁盘、IO、连接数五项齐全，
> 实际上漏了 FD、inode、写满预测、IOPS 四项。**

原因是设计指标时按**"资源种类"**枚举（CPU/内存/磁盘/网络），
而不是按**"资源耗尽的失效模式"**枚举。而同一份资源有多种耗尽方式
（块满 / inode 满 / FD 满 / 配额满），每一种都独立失效。

同理，A 类看起来有 5 个 HTTP 指标很全，但漏了**流量归零**——
因为"QPS"这个词在设计时只被理解为"多不多"，没被理解为"有没有"。

> 建议写进 `docs/alarm/metrics.md` §5「扩展规则」：
> 新增指标前先问「它对应哪一类失效模式，该类是否已覆盖」，
> **不要按资源清单逐项打勾**。

## 5. 本文的验证边界

- 本文全部为**设计分析**，未修改任何代码。
- 「现有 28 个指标的覆盖情况」逐条回读 `metrics.md` 与 `contract.md` 核对。
- 「前端死胡同」已**实测确认**：`policy-form.vue:944` 遍历全部 5 项、
  `policy-logic.ts:142-144` 的 3/4/5 均为 `[]`、`policy-form.vue:986` 的提示文案。
- 「R2 暴露时长」是设计判断，非实测——需要真实告警数据校准。
- 建议将 §3.1 的 11 个指标在**有真实监控数据源**的团队评审下确认阈值，
  本文给出的 `defaultThreshold` 仅为占位。
